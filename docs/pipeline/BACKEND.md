# Catalog and permission-gated enrichment

The new migration adds safe public catalog records, private provenance, website permissions, jobs, search cache, hashed search quotas and atomic weekly call budgets. It leaves existing room behavior intact and extends candidate source validation to Overture. No cloud project, billing, Cron job or paid API call has been activated. **No approved websites are supplied.** Fictional menu/permission examples occur only in rollback tests.

## Server configuration

Copy the server-only fields from `.env.example` into the intended server environment. `SUPABASE_SECRET_KEY` is a server secret/service-role credential, never a browser publishable key. Do not use `VITE_*` for server secrets. With no database configuration, catalog reads return empty results, cache reads return null and quota checks defer to the existing in-memory controls. A configured database failure throws; the caller should report or explicitly fall back without pretending persistence succeeded. Imports require a configured server credential and cannot be written from anonymous clients.

`readNearby` returns up to 100 published places inside the requested radius; callers recompute distance for the query origin. `ingestPlaces` accepts at most 100 normalized records. `getCachedDiscovery` / `putCachedDiscovery` use five-minute durable entries. `consumeSearchQuota` accepts a SHA-256 hexadecimal IP digest and atomically limits twelve searches per UTC minute. Never persist raw IPs. Retention cleanup removes expired search caches and old quota buckets. These guards do not replace gateway/DDoS controls or appropriate upstream usage quotas.

Published catalog fields use a whitelist. Unknown/pending price and diet always remain null, images remain absent, pending cuisine proposals are stripped, and private source documents/results never enter public snapshots. All new tables enable RLS. Catalog/permission/job RPCs are executable only by service_role. AI results go exclusively to private jobs as `pending_review`; there is no automatic publication or AI approval operation. A future human moderation interface must explicitly verify evidence and record reviewer provenance before implementing hard-fact publication.

## Permission workflow — future activation only

An administrator must document permission for each **exact HTTPS URL**, a reference to the owner's approval, identity of the reviewer, expiry, positive revision, and explicit crawl, reuse and third-party-processing scopes. Store these in `saantayo_private.website_permissions`. Changing or revoking scope must increment revision. Neither discovering a website nor its public accessibility establishes permission. Do not add entries for a business without its documented approval.

Each source passes safe HTTPS/no credentials/no unusual port validation, all-address DNS checks and a pinned public IPv4 request. The pilot deliberately skips IPv6-only or mixed unsupported address sets. It fetches robots.txt and fails closed if missing, inaccessible, redirected, non-text or denied. It then fetches only the approved URL, refusing every redirect. Ten-second requests and 64KB source/32KB robots limits prevent unbounded downloads. HTML scripts, embeds and external resource references are removed; source business text is capped at 6KB before any paid attempt.

Firecrawl's scrape API has no documented hard redirect or DNS pinning control. Consequently this implementation uses its [file parse API](https://docs.firecrawl.dev/api-reference/endpoint/parse) on sanitized text uploaded as an inert escaped HTML document, rather than delegating browsing to a vendor. Vendor zero-data-retention is requested. Only a single cleaned file is submitted, no deep crawl, search, browser actions or vendor private-cache lookup. The cleaned markdown must remain under 6KB. The exact original locally fetched text remains the evidence authority.

Gemini calls the official REST endpoint with exact model [`gemini-3.5-flash-lite`](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite), JSON MIME type and [`responseFormat.text.schema`](https://ai.google.dev/gemini-api/docs/generate-content/structured-output). No grounding/browsing tools are enabled. The serialized input is capped at 10KB, used as a conservative token upper bound, and output is capped at 2,048 tokens. Claim validation requires exact complete source lines and matching contextual values; mismatched amounts, currencies, units, unlabeled cuisine and inferred whole-venue diet are rejected. Even supported claims remain pending manual review. Unsupported real-world menu layouts may yield no accepted claims by design.

## Budgets and protected execution

`POST /api/enrich` requires the server-only bearer `ENRICHMENT_JOB_SECRET`, checked through constant-time digest comparison. The pipeline also requires `ENRICHMENT_ENABLED=true`; default false performs zero paid calls. A job reservation is unique by UTC week + exact source URL + permission revision. Weekly budget-row and per-job locks enforce at most **2 jobs, 2 Firecrawl calls, 2 Gemini calls, 20,000 reserved input tokens**. Each vendor slot is reserved before its request. Expired/revised permissions fail revalidation before spending. Failed or timed-out paid attempts remain consumed; there is no automatic retry, duplicate call, refund or quota reset. This is a hard usage cap, not a guaranteed dollar amount; provider pricing and credits need review before activation.

The weekly installer is a separate inactive SQL file (`supabase/install_weekly_enrichment.sql`). It is not applied by migrations. It refuses to run without explicit session enablement, approved websites and Vault endpoint/strong secret. It assumes previously authorized pg_cron/pg_net/Vault provisioning. Schedule is Monday 02:00 UTC (10:00 Singapore/Philippines). Do not run it until the user explicitly authorizes scheduling and hosting.

## Validation and remaining checks

Local tests cover evidence semantics, private/reserved IPs, permission expiry/scopes, robots and disabled-paid execution, endpoint authorization, and exact Gemini schema/model. `supabase/catalog_security_test.sql` is a transactional rollback check for public sanitization, anonymous restrictions, durable search quota, expired approvals, idempotency, call limits, failed-attempt consumption, two-job limits and permission revision changes. The migration and regression script run successfully on disposable PostgreSQL 16 with mocked Supabase roles. Existing room regression tests must also remain green.

No live Firecrawl, Gemini, Supabase Auth/Realtime, cloud database, production Cron or vendor-retention guarantee has been tested. Provider fixtures and SQL permission rows are fictional. Before future activation, verify provider upload support and response format with one explicitly approved source and a separately approved paid budget; confirm account-level retention and billing settings, database advisors and protected endpoint hosting.
